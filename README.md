README
============================

This website is based on the [Yii 2](http://www.yiiframework.com/) framework and the Yii 2 CMS extension [yii2-cms](https://github.com/davidhirtz/yii2-cms/).


Requirements
------------

This project requires PHP 8.3 or higher, MySQL or MariaDB, ImageMagick and, for the assets, Node.js 20.19 or higher. Detailed requirements can be found by running [Composer](http://getcomposer.org/).


Installation
------------

<!-- template -->
### A new project

```bash
composer create-project davidhirtz/yii2-cms-template my-site
```

The installer asks for the project's name, the preset and the database. There are two presets:

- **bare** – the layout, the cookie banner and two text section types ("Column", "Full width"), for a project that brings its own design.
- **starter** – nine more section types, each with a view of its own in `resources/views/site`: hero banner, image & text, text & image, carousel, gallery, quote, call to action, accordion and teasers of linked pages. `/admin/cms/setup` then creates a home page that shows the ones that need no images, and the imprint and privacy pages the cookie banner links to.

The installer creates both databases (`<name>` and `<name>_test`), writes `config/db.php`, `config/params.php` and `config/local.php`, migrates, creates the first user and makes the "Initial commit" — then removes itself.

Every answer can be given ahead as an environment variable for a run with `--no-interaction`: `INSTALL_NAME`, `INSTALL_SLUG`, `INSTALL_PACKAGE`, `INSTALL_LICENSE`, `INSTALL_PRESET`, `INSTALL_DB_HOST`, `INSTALL_DB_NAME`, `INSTALL_DB_USER`, `INSTALL_DB_PASSWORD`, and `0` or `1` for `INSTALL_MIGRATE`, `INSTALL_USER`, `INSTALL_NPM` and `INSTALL_GIT`. If it stops half way, fix the cause and run `composer run-script post-create-project-cmd` again.

### An existing project

```bash
git clone git@github.com:OWNER/REPOSITORY.git
cd REPOSITORY
composer install
composer install-hooks
npm install
```

Then create `config/params.php` and `config/db.php` as described under "Configuration" below, and the first user with `php yii user/create`. A server installs with `composer install --optimize-autoloader --no-dev` instead.

### Running it locally

```bash
YII_ENV=local php -S localhost:8080 -t web
```

`local` loads the gitignored `config/local.php`, which the installer writes; without one, use `YII_ENV=dev`. Sign in at `/admin` and open `/admin/cms/setup` once to create the home page — until then `/` answers with a 404. Apache serves `web/` as the document root with the rewrite rules of `web/.htaccess`.


Configuration
-------------

### Credentials

Run `php yii params` to create the configuration file `config/params.php` with your sensitive information, which should not be added to the version control.
The file must include a cookie validation key, which will be auto-generated by running the command for the first time.

```php
<?php
return [
    'cookieValidationKey' => 'AUTO-GENERATED-COOKIE-VALIDATION-KEY',
    //'cookieDomain' => '.DOMAIN.COM',
    //'email' => 'YOUR-EMAIL',
    //'mailerDsn' => 'smtp://YOUR-SMTP-CONNECTION-STRING',
];
```


### Database

Apply the database migrations by running the command `php yii migrate`. This will also set up the database configuration before applying the migrations.
The database credentials are saved to `config/db.php`.

```php
<?php
return [
    'dsn' => 'mysql:host=127.0.0.1;dbname=DATABASE',
    'username' => 'USER',
    'password' => 'PASSWORD',
];
```

The migrations seed a tenant for the installation. Visit `/admin/cms/setup` once as an administrator afterwards to create the index entry.


### Registry (optional)

An installation can report itself to a version registry: `php yii registry/push` posts what the system *Application* tab shows — name, version, commit, the installed extensions, PHP, database, Yii and the migration state — to `params.registryUrl`, authenticated with `params.registryKey`. `php yii registry/show` prints the same report without sending it. Most installations need none of this and can skip the section.

```bash
php yii params/create registryUrl https://REGISTRY-HOST/registry/push
php yii params/create registryKey <the key>
```

Leaving both parameters unset is not an error, and neither is a registry that is down or a key that was revoked: the command warns and exits 0, which is why the deploy carries it as the last step inside the maintenance window. `--strict` turns both into a failure instead.


### Deployment

Every push runs the checks on GitHub (the `check` job of `.github/workflows/deploy.yml`), and the deploy waits for them. The deploy is keyed by branch on a repository variable, and a branch without one is skipped. The server is named by variables too, so every project uses the same workflow:

| Variable               | What it does                                                                            |
|------------------------|-----------------------------------------------------------------------------------------|
| `DEPLOY_PATH_<branch>` | the directory on the server the deploy runs in; unset, nothing deploys                  |
| `SSH_HOST`             | the server the deploy connects to                                                       |
| `SSH_USERNAME`         | the user it connects as, with the private key in the `SSH_KEY` secret                   |
| `PHP`                  | the PHP binary on the server; unset, `php`                                              |

A `composer.phar` in the deploy path is used when there is one, the global `composer` otherwise.


### Permissions

Directories `runtime`, `web/assets` and `web/uploads` need write permissions for web and console user. These permissions are automatically set when running `composer install`.


### Development

The environment is selected by the `YII_ENV` environment variable and decides which `config/<env>.php` is loaded. It defaults to `prod`; `dev` and the gitignored `local` enable debugging.

```bash
YII_ENV=dev php yii <command>
```

CSS and JavaScript assets are processed with [Vite](https://vitejs.dev/) and need to be recompiled after a change. Run `npm install` to install the development dependencies, `npm run dev` to start the Vite development server or `npm run build` to compile the assets for production. The compiled files in `web/dist` are committed and the deploy does not build them, so commit `web/dist` with every CSS or JavaScript change.


### Checks

Code style, static analysis and the test suite are the three gates a change has to pass. `vendor/bin/check` runs all of them against the working tree and is also what the committed `.githooks/pre-push` runs, so the check you run by hand and the one that guards a push cannot drift apart.

The script and the tool configurations behind it come from [yii2-dev](https://github.com/davidhirtz/yii2-dev), the one `require-dev` entry this project has, so they cannot drift between projects either: a change to the gates arrives with a `composer update` rather than being copied by hand. `.php-cs-fixer.php`, `rector.php` and `phpstan.neon` are left here holding only the directories to look at, which is the one thing that differs per project.

```bash
composer check
```

It reports and never rewrites: a style failure asks for `composer cs-fix` rather than fixing the tree under a commit that is already made. `composer install-hooks` points `core.hooksPath` at `.githooks` and is needed once per clone — a hook under `.git/hooks` is not committed. `git push --no-verify` skips the gate deliberately.

The same checks run on GitHub before a deploy; the hook reports a failure before the push rather than after it.

The individual commands, for when only one of them is wanted:

```bash
composer cs-fix
composer phpstan
composer test
```

The tests run against their own database, `cms_template_test` by default, configured by `config/test.php` and overridable through `MYSQL_DSN`, `MYSQL_USER` and `MYSQL_PASSWORD`. Create it once; `check` migrates it on every run, so a new migration needs no separate step.

```bash
YII_ENV=test php yii migrate --interactive=0
```


### Translations

Messages are addressed by `UPPER_SNAKE_CASE` key, never by English text, and the key and category must be string literals in the `Yii::t()` call itself — anything reached through a variable or a ternary is invisible to the extractor and is deleted from every language file on the next run.

```bash
php yii message messages/config.php
```


### Cookie consent

The banner (`layouts/_cc.php`) and its script render what the skeleton's `consent` component describes. The
categories and services are configured in `config/prod.php`; the skeleton README's "Cookie consent" lists the
services it ships (Google Analytics, Tag Manager, Ads, Maps, YouTube, Vimeo) and shows how to add any other. Per
project:

- Set `gtagId` in `config/params.php` to a Google Tag Manager container (`GTM-…`) or a Google Analytics stream (`G-…`).
  The "Analytics" category is offered only then; nothing of Google's loads before a visitor allows it, and Consent Mode
  v2 signals tell the tags what was allowed. A container sees the choice as the `cc_update` event and its
  `cc_categories` variable.
- List every service the site embeds (booking forms, podcasts, maps) under `ExternalCategory` and every tag a Tag
  Manager container adds under `AnalyticsCategory` or `MarketingCategory`, and adjust the banner texts in `messages/`.
- A changed service or cookie asks every visitor again on its own: the stored and logged version includes a
  fingerprint of them. Raise the component's `version` when only the wording changed but visitors should be asked
  again.
- With `YII_DEBUG`, the browser console warns about every first-party cookie the list does not declare. Click through
  the site with everything allowed before going live and after adding a tag. Cookies an iframe sets on its provider's
  domain are invisible to the script, so they are listed from the provider's documentation (`thirdParty()`).

Every decision is logged with a random ID, the version and the categories, without an IP address, and listed in the
admin under "System" → "Cookie consents" (`enableConsentLog` on the admin module). Keep the log as long as the
consent plus the limitation period and clear it from a cron job:

```php
'modules' => [
    'admin' => [
        'consentLifetime' => 4 * 365 * 86400,
    ],
],
```

```bash
php yii consent/clear
```


Structure
-------------------

      app/                the PSR-4 application root, containing custom application models, components, controllers and widgets
      config/             application and database configurations
      messages/           translation files for multilingual pages
      node_modules/       3rd-party NPM libraries (development only)
      resources/          uncompiled CSS and Javascript files and the view templates
      runtime/            cache and log files generated during runtime
      tests/              tests for the application
      vendor/             dependent 3rd-party packages
      web/                the webroot, containing the entry script, published resources and uploads
