README
============================

This website is based on the [Yii 2](http://www.yiiframework.com/) framework and the Yii 2 CMS extension [yii2-cms](https://github.com/davidhirtz/yii2-cms/).


Requirements
------------

This project requires PHP 8.3 or higher, MySQL or MariaDB and ImageMagick. Detailed requirements can be found by running [Composer](http://getcomposer.org/).


Installation
------------

Fetch source code via GIT.

```bash
git init
git remote add origin git@github.com:davidhirtz/REPOSITORY.git
git fetch origin
git branch main origin/main
git checkout main
```

If you do not have [Composer](http://getcomposer.org/) installed, you may install it by following the instructions at [getcomposer.org](http://getcomposer.org/doc/00-intro.md#installation-nix).
On Linux and Mac OS X, you'll run the following commands:

```bash
curl -sS https://getcomposer.org/installer | php
```

You can then install the dependencies using the following command:

```bash
php composer.phar install --optimize-autoloader --no-dev
```

Configuration
-------------

### Credentials

Run `php yii params` to create the configuration file `config/params.php` with your sensitive information, which should not be added to the version control.
The file must include a cookie validation key, which will be auto-generated by running the command for the first time.

```php
<?php
return [
    'cookieValidationKey' => 'AUTO-GENERATED-COOKIE-VALIDATION-KEY',
    //'cookieDomain' => '.DOMAIN.COM',
    //'email' => 'YOUR-EMAIL',
    //'mailerDsn' => 'smtp://YOUR-SMTP-CONNECTION-STRING',
];
```


### Database

Apply the database migrations by running the command `php yii migrate`. This will also set up the database configuration before applying the migrations.
The database credentials are saved to `config/db.php`.

```php
<?php
return [
    'dsn' => 'mysql:host=127.0.0.1;dbname=DATABASE',
    'username' => 'USER',
    'password' => 'PASSWORD',
];
```

The migrations seed a tenant for the installation. Visit `/admin/cms/setup` once as an administrator afterwards to create the index entry.


### Registry

The installation reports itself to the version registry: `php yii registry/push` posts what the system *Application* tab shows — name, version, commit, the installed extensions, PHP, database, Yii and the migration state — to `params.registryUrl`, authenticated with `params.registryKey`. `php yii registry/show` prints the same report without sending it.

```bash
php yii params/create registryUrl https://registry.davidhirtz.com/registry/push
php yii params/create registryKey <the key>
```

Leaving both parameters unset is not an error, and neither is a registry that is down or a key that was revoked: the command warns and exits 0, which is why the deploy carries it as the last step inside the maintenance window. `--strict` turns both into a failure instead. A console application knows no URL of its own, so the deploy passes `--url`; without it the installation reports itself as an unnamed local one.

The deploy is keyed by branch on a repository variable, and a branch without one is skipped:

| Variable                | What it does                                                                        |
|-------------------------|-------------------------------------------------------------------------------------|
| `DEPLOY_PATH_<branch>`  | the directory on the server the deploy runs in; unset, nothing deploys                |
| `REGISTRY_URL_<branch>` | the installation's own URL, passed to `registry/push`; unset, nothing is reported     |


### Permissions

Directories `runtime`, `web/assets` and `web/uploads` need write permissions for web and console user. These permissions are automatically set when running `composer install`.


### Development

The environment is selected by the `YII_ENV` environment variable and decides which `config/<env>.php` is loaded. It defaults to `prod`; `dev` and the gitignored `local` enable debugging.

```bash
YII_ENV=dev php yii <command>
```

CSS and JavaScript assets are processed with [Vite](https://vitejs.dev/) and need to be recompiled after a change. Run `npm install` to install the development dependencies, `npm run dev` to start the Vite development server or `npm run build` to compile the assets for production.


### Checks

Code style, static analysis and the test suite are the three gates a change has to pass. `vendor/bin/check` runs all of them against the working tree and is also what the committed `.githooks/pre-push` runs, so the check you run by hand and the one that guards a push cannot drift apart.

The script and the tool configurations behind it come from [yii2-dev](https://github.com/davidhirtz/yii2-dev), the one `require-dev` entry this project has, so they cannot drift between projects either: a change to the gates arrives with a `composer update` rather than being copied by hand. `.php-cs-fixer.php`, `rector.php` and `phpstan.neon` are left here holding only the directories to look at, which is the one thing that differs per project.

```bash
composer check
```

It reports and never rewrites: a style failure asks for `composer cs-fix` rather than fixing the tree under a commit that is already made. `composer install-hooks` points `core.hooksPath` at `.githooks` and is needed once per clone — a hook under `.git/hooks` is not committed. `git push --no-verify` skips the gate deliberately.

A push to a branch with a deploy path deploys it and nothing on the way there runs these checks, so this hook is the only gate between a broken commit and the server.

The individual commands, for when only one of them is wanted:

```bash
composer cs-fix
composer phpstan
composer test
```

The tests run against their own database, `cms_template_test` by default, configured by `config/test.php` and overridable through `MYSQL_DSN`, `MYSQL_USER` and `MYSQL_PASSWORD`. Create it once; `check` migrates it on every run, so a new migration needs no separate step.

```bash
YII_ENV=test php yii migrate --interactive=0
```


### Translations

Messages are addressed by `UPPER_SNAKE_CASE` key, never by English text, and the key and category must be string literals in the `Yii::t()` call itself — anything reached through a variable or a ternary is invisible to the extractor and is deleted from every language file on the next run.

```bash
php yii message messages/config.php
```


### Cookie consent

The banner, its cookie list and the script configuration all come from `App\Consent\Consent`. Per project:

- Set `gtagId` in `config/params.php` to a Google Tag Manager container (`GTM-…`) or a Google Analytics stream (`G-…`).
  The "Analytics" category is offered only then; nothing of Google's loads before a visitor allows it, and Consent Mode
  v2 signals tell the tags what was allowed. A container sees the choice as the `cc_update` event and its
  `cc_categories` variable.
- List every service the site embeds (booking forms, podcasts, maps) in `getExternalCategory()`, every tag a Tag Manager
  container adds in `getAnalyticsCategory()`, and adjust the texts in `messages/`.
- Raise `Consent::VERSION` whenever the list changes: every visitor is asked again, and the log shows which version a
  visitor agreed to.
- With `YII_DEBUG`, the browser console warns about every first-party cookie the list does not declare. Click through
  the site with everything allowed before going live and after adding a tag. Cookies an iframe sets on its provider's
  domain are invisible to the script, so they are listed from the provider's documentation (`thirdParty: true`).

Every decision is logged with a random ID, the version and the categories, without an IP address, and listed in the
admin under "System" → "Cookie consents" (`enableConsentLog` on the admin module). Keep the log as long as the
consent plus the limitation period and clear it from a cron job:

```php
'modules' => [
    'admin' => [
        'consentLifetime' => 4 * 365 * 86400,
    ],
],
```

```bash
php yii consent/clear
```


Structure
-------------------

      app/                the PSR-4 application root, containing custom application models, components, controllers and widgets
      config/             application and database configurations
      messages/           translation files for multilingual pages
      node_modules/       3rd-party NPM libraries (development only)
      resources/          uncompiled CSS and Javascript files and the view templates
      runtime/            cache and log files generated during runtime
      tests/              tests for the application
      vendor/             dependent 3rd-party packages
      web/                the webroot, containing the entry script, published resources and uploads
